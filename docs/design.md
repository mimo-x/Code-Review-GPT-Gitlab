# review_core 设计说明：第 0–2 阶段

本文记录 `review_core` 前三个阶段的设计、实现、实测数据，以及讨论中做出的取舍：

- 第 0 阶段：让 bench 的输入正确；
- 第 1 阶段：确定性分诊；
- 第 2 阶段：完善 Code Intel 和工具层。

调查 agent 和验证器属于之后的阶段，本文不涉及。

## 1. 目标与约束

**目标：** 在 AACR-Bench 上，用与 OpenCodeReview（OCR）相同的模型超过它。OCR 的成绩是 SEM-F1 25.10%，精确率 33.9%，召回率 20.0%。主要靠提高召回取胜，总 token 消耗不超过 OCR 的 1.5 倍。

**三个核心论点：**

1. 结构化的代码情报（符号、调用、引用）能提高召回。
2. 调查以假设驱动，每个结论都要有证据。
3. 验证独立进行，验证者拿到的证据与调查者对称。

**分工原则：** 事实用规则判定，判断交给 agent，资源按运行时观测分配。

**工程约束：**

- **核心与 bench 解耦。** `review_core` 不知道 AACR 的存在，只接收“仓库 + 几个固定 SHA”。bench 相关逻辑全部放在 `review_bench`，依赖方向只能是 `review_bench → review_core`。以后接入 GitLab 业务时，MR 的 `diff_refs` 里本来就有合并基点，直接调用核心即可。
- **可复现。** 同一个快照加同一份配置，分诊结果逐字节一致，计划 id 也一致。
- **任何改动都不会被悄悄丢掉。** 每个改动行要么被某个簇审查，要么带着证据被排除，并由不变量校验保证。

## 2. 总体结构

```
review_bench.aacr ──► review_core
                       ├─ workspace/   快照：固定 SHA 的树、diff、文件读取、文本搜索
                       ├─ intel/       Code Intel：语法、符号、改动单元、改动图、引用（第 6 节）
                       │   ├─ resolvers/  可选的类型感知解析辅助程序：Go / Java / C++（6.3）
                       │   ├─ precise.py  把解析结果映射回符号
                       │   ├─ tools.py    给 agent 的工具；render.py 负责文本输出（6.5）
                       ├─ triage/      分诊：把改动拆成审查任务（第 4 节）；brief.py 渲染按簇简报
                       ├─ tokens.py    token 计数（中立模块）
                       └─ textshape.py 文本形状与长行折叠（中立模块）
```

依赖方向：`triage → intel → workspace`。`tokens.py` 和 `textshape.py` 不依赖任何业务模块，intel 和 triage 都可以使用，这样避免了 intel 反向依赖 triage。

后续阶段会在 triage 之后加入调查 agent（按簇并发）和验证器，它们消费 `TriagePlan`。

## 3. 第 0 阶段：让 bench 的输入正确

### 3.1 发现的问题

| 问题 | 影响 |
|---|---|
| bench 缓存的仓库是浅克隆，导入时 `git fsck` 失败（exit 2） | 一个用例都跑不了 |
| diff 用的是两点 `base..head`，不是 PR 实际的 `merge-base...head` | 120 个用例的 diff 是 PR 实际改动的 5 倍以上；`cline` 的一个用例 diff 有 76,065 行，PR 实际只有 11 行 |
| Git 失败时只保留 exit code | 无法排查问题 |

### 3.2 修复

- **Workspace 导入只复制被固定的提交树。** 审查只需要几个提交的树，不需要历史。导入时只复制这几个提交的对象，在目标仓库里登记为 shallow 边界，再按 shallow 语义校验连通性。源仓库是浅克隆还是完整克隆，导入方式都一样，导入量也更小。
- **diff 按合并基点生成。** 由 `review_bench.aacr` 负责：
  - `cases.py` 读取用例；
  - `sources.py` 通过 GitHub compare 接口拿到合并基点，记录到 `merge-bases.json`，再按深度 1 补拉该提交；
  - `prepare.py` 以 `merge-base...head` 生成快照，PR 原来的 base 记为 `start_sha`。
- **离线可复现。** “算不出合并基点”这个结果本身也会被记录下来，离线重跑时这类用例直接标记为不可用，不会失败，也不会退回到两点 diff。
- **报错保留脱敏后的 stderr。** 只保留一行，URL 里的凭据替换为 `***`。

### 3.3 结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 可生成快照的用例 | 0 | 189 / 200 |
| diff 行数 / catalog 行数 | 偏差可达数千倍 | 中位数 0.97，P10–P90 为 0.52–1.21 |

**不可用的 11 个用例：** 6 个在 bench 缓存里本来就没有源码；5 个（keycloak 4 个、ClickHouse 1 个）的 head 是从归档恢复的，GitHub 已没有这个提交，算不出合并基点。各 split 的可用数：dev 110/115，calibration 36/41，holdout 39/40，smoke 10/10。

相关提交：`55f5c24`、`3e08b66`。

## 4. 第 1 阶段：确定性分诊

### 4.1 职责

**输入：** Code Intel 构建的改动图 `ChangeGraph`，包括：

- **改动单元（unit）：** 一个被改动的符号，或者一组不属于任何符号的改动行；
- **单元之间的关系：** 调用、import、测试引用、同文件、疑似重命名。

**输出：** `TriagePlan`，其中包括：

- 有序的簇（每个簇是一个审查任务，带预算）；
- 初始假设（种子）；
- 覆盖清单；
- 全局改动目录；
- 共享预算池；
- 完整性标记和问题列表。

计划以确定性 id 存入 SQLite 的 `triage-plans-v1` 集合，可以用 `review-core plan --snapshot S --id ID` 重新载入。

**分诊里不调用 LLM。** 理由有三：省掉一次模型调用；结果可复现、可测试；需要判断的问题留给拿着完整上下文的调查 agent。

### 4.2 流水线

```
过滤 → 建边 → 聚类（Kruskal + 容量上限）→ 相邻打包 → 规模分层 → 种子 → 排序 → 预算 → 改动目录 → 覆盖校验
```

#### ① 过滤：只凭硬证据排除（`triage/filter.py`）

可以排除的只有以下几类：

| 原因 | 判定依据 |
|---|---|
| `binary` | Git 报告为二进制 |
| `lock_file` | 文件名属于已知的依赖锁文件（`package-lock.json`、`go.sum`、`uv.lock` 等 22 种） |
| `minified` | 后缀为 `.min.js` / `.min.mjs` / `.min.css` |
| `generated` | source map，或 Code Intel 判定为生成文件（`linguist-generated` 属性，或文件头有 “do not edit” 加 “generated”） |
| `format_only` | 改动只涉及空白，而且语法完全相同，见下 |

纯格式要同时满足两个条件：

1. **文本条件：** 去掉全部空白后，增删内容相同。
2. **语法条件：** 改动前后的语法树相同。比较时，字符串字面量（包括模板字符串、字符字面量）按原文整体比较，因为字符串里的空白是内容，不是格式。
   - 单元两侧都有符号时，比较两个符号；
   - 符号片段单独解析不了时，比较整个文件。只要文件里还有其他改动，这个单元就照常审查，这是偏保守的选择。

任何一侧解析失败、有语法错误，或者语言未知（文档、未知格式），都不按格式排除。

早期版本只用文本条件就判定，对 JS/Go 等语言跳过语法检查。外部审阅复现了两类漏审：JS 字符串 `"a b"` 改成 `"ab"`，以及 Python 多行字符串里删掉一个空行，都被误判为纯格式而排除。覆盖校验发现不了这类问题，因为它只检查每个单元是否有归属，不检查排除得对不对。修复后，bench 上纯格式排除从 135 个单元降到 8 个。抽样核对被放回审查的单元，大多是“文件里还有其他改动，只加了一个空行”，偏保守地照常审查，总预算只增加了 0.3%。

每条排除都记录原因、证据和涉及的行，进入覆盖清单。

#### ② 建边（`triage/links.py`）

把单元之间的事实变成带权重的边，同一对单元只保留最强的一条，低于 `min_link_weight`（0.2）的丢弃。

| 边 | 来源 | 权重 |
|---|---|---|
| `call/bound` | Code Intel，绑定确定的调用 | 1.0 |
| `test_reference/bound` | Code Intel，测试里的确定调用 | 0.9 |
| `test_pair` | 分诊：`foo` ↔ `test_foo` / `foo_test` / `foo.spec` / `FooTest` / `TestFoo` | 0.9 |
| `rename_candidate` | Code Intel，语法相似度 ≥ 0.8 | 0.7 |
| `call/candidate`、`test_reference/candidate` | Code Intel，按名字匹配的候选调用 | 0.6 |
| `mention` | 分诊：改动行里出现了另一个改动符号的名字（名字长度 ≥ 3，被不超过 3 个单元拥有） | 0.6 |
| `same_file` | Code Intel | 0.5 |
| `import/bound`、`import/candidate` | Code Intel | 0.4 / 0.3 |
| `same_directory` | 分诊，按目录做星形连接，避免产生平方级的边 | 0.2 |

`mention`、`test_pair`、`same_directory` 不依赖语言解析。加入它们，是因为 Java、Go、C++ 目前拿不到确定的调用关系，只靠 Code Intel 的边几乎无法合并（见第 6 节）。

#### ③ 聚类（`triage/clustering.py`）

- **单元大小：** diff 文本的 token 数，加每行 2 个 token。
- **合并规则：** Kruskal 加并查集。边按（权重降序、source、target）排序，依次尝试合并；只有合并后的簇不超过 `max_cluster_tokens`（6000）且单元数不超过 `max_cluster_units`（24）时才合并。
- **不拆分单元：** 本身就超过上限的单元单独成簇，标为 `oversized`。函数切开审会丢失上下文；内容过长的问题交给工具层分页处理。

#### ④ 相邻打包

把剩下的小簇（小于 `pack_tokens` = 1500）按路径排序，在同一个顶层目录内，按容量依次装到一起。打包产生的边类型是 `locality`，权重为 0，agent 由此知道这些单元只是路径相邻。

这一步来自实测：不打包时，`FreeCAD@a050e42` 会被拆成 59 个簇（52 个只有一个单元），总预算 48.5 万 token；打包后是 8 个簇、10.3 万 token。

#### ⑤ 规模分层（`triage/bulk.py`、`intel/service.py`、`intel/tools.py`）

规模本身不能作为“不审”的理由，但会影响“怎么审”。分三层处理：

| 层 | 条件 | 处理 | 所在模块 |
|---|---|---|---|
| 长行 | 单行超过 2000 字符 | 工具输出中折叠：显示前 2000 字符，附上剩余字符数、字母占比，以及继续读取的参数；`read_file` 用 `char_offset` 分页 | 工具层 |
| 不建索引 | 文件超过 1MB（`CodeIntel.max_index_bytes`） | 不做语法解析、不建索引；引用查找和结构搜索都跳过它；仍可作为文本读取。该文件的单元全部成为 bulk | Code Intel |
| 数据型改动 | 单元改动 ≥ 20000 字符，并且长行字符占比 ≥ 50%，或字母占比 ≤ 20% | 成为 bulk | 分诊 |

bulk 单元的处理方式：

- **不参与建边和打包：** 每个文件的 bulk 单元合成一个独立的簇。
- **排在最后：** 所有普通簇之后。
- **只给保底预算：** 6000 token，不随大小增加。
- **仍然审查：** 在改动目录里标为 `(bulk)`，并保留在覆盖清单的审查部分。

这是“审查形态”的决定，不是排除。

工具层的配套改动：

- 证据记录保留完整内容，只有给模型看的视图被折叠。
- `read_file` / `read_symbol` 只输出一份带行号的源码。原来原文和带行号版本各输出一遍，token 翻倍。
- `read_diff` 不再附带与 hunks 重复的原始 patch。
- 单个文件的 diff 超出输出上限时，原来会返回空结果。第 1 阶段先改为退化成按 hunk 的摘要，第 2 阶段改为按 hunk 分页，单个 hunk 还能按行续读（见 6.5）。
- 不建索引的文件不会被悄悄跳过：定义查找和结构搜索遇到这类文件时，返回 `complete=false` 并写明哪个文件没有检查，提示 agent 改用 `code_search` 或 `read_file`。否则 agent 会把“没找到”误当成“不存在”。

#### ⑥ 种子（`triage/seeds.py`）

种子是开始调查前用规则种下的初始假设，不是结论。所有候选名字合成一次 `git grep -F -w` 批量搜索 head 版本，得出两类种子：

- **`dangling_reference`：** 被删除的符号没有以同名同类重新加回来，但 head 上仍有引用。
- **`unchanged_callers`：** 非私有的函数或方法改了签名，但有调用处不在本次 diff 里；匹配时排除 diff 内的命中，也排除符号自身定义体里的命中。

降噪规则：

- 名字短于 4 个字符的不搜；
- 文档文件里的命中不算；
- 类和结构体的签名变化不算；
- 单个名字命中超过 50 处时太泛，不生成种子，只记一条 issue。

命中按（是否在 diff 内、是否与所属符号同文件、路径、行号）排序，每个种子最多附 5 处位置。

#### ⑦ 排序（`triage/ordering.py`）

| 事实 | 加分 |
|---|---|
| 每个种子 | +3（最多计 3 个） |
| 有非私有签名改动 | +2 |
| 有删除的符号 | +2 |
| 源码行为改动 | +1 |

排序键为（是否 bulk，分数降序，大小降序，首个单元的位置）。簇编号 `C#` 和单元编号 `U#` 都按这个顺序分配，被排除的单元编号排在最后。

#### ⑧ 预算（`triage/budget.py`）

```
普通簇：clamp(6000 + 3 × diff_tokens + 2000 × 种子数, 6000, 30000)
bulk 簇：6000
共享池：全部初始预算 × 25%
```

`BudgetLedger` 负责运行时从池里追加预算，规则如下：

- 申请必须引用本簇里开放的 major 假设，否则拒绝；
- 单个簇的总预算不超过 48000；
- 池子耗尽后不再发放；
- 账本线程安全；每次决定都记录为一条 `Grant`。

**当前目标：** 保证每个需要审查的簇都有预算。参数尚未校准，等调查 agent 跑起来、和 OCR 的实际消耗对比后再调。

**预算的单位（第 3 阶段已定）：** 预算按“模型输入加输出的 token 数”计量。分诊给出的是各簇之间的相对份额，agent 运行时把它乘以系数 `budget_scale`，再加上按比例分到的共享池，得到每个回合实际可用的 token 数（见 10.5）。这个系数在 calibration 集上校准。目前 agent 默认不计预算（`ReviewConfig.budget_enabled = false`）：分配方式还没校准，先让回合只受步数和上下文上限约束，记录实际用量，之后再据此设计预算。

#### ⑨ 改动目录（`triage/catalog.py`）

所有簇共享一份约 3000 token 的目录，列出每个单元的编号、名字、改动类型和增删行数，让审查某个簇的 agent 也知道整个 MR 改了什么。放不下时先退到按文件汇总，再不行就截断，并注明省略了多少行。

#### ⑩ 收尾

- **覆盖不变量：** 每个改动单元恰好属于一个簇，或者恰好被排除一次，否则直接抛 `RuntimeError`。
- **完整性：** 计划汇总改动图和种子搜索的 `limits`、`gaps`、`issues`（含义见 6.1），列表最多各保留 20 条，`gap_counts` 记录各类缺口的总数。`complete` 由这三个字段推导出来。

### 4.3 配置一览（`TriageConfig`）

| 分组 | 字段 | 默认值 |
|---|---|---|
| 聚类 | `max_cluster_tokens` / `max_cluster_units` / `min_link_weight` / `pack_tokens` | 6000 / 24 / 0.2 / 1500 |
| 规模 | `max_line_chars` / `bulk_min_chars` / `bulk_long_line_share` / `bulk_max_letter_share` | 2000 / 20000 / 0.5 / 0.2 |
| 种子 | `min_seed_name_length` / `max_seed_symbols` / `max_seed_hits_per_symbol` / `max_seed_locations` / `seed_search_timeout` | 4 / 200 / 50 / 5 / 30s |
| 预算 | `floor_tokens` / `cap_tokens` / `ceiling_tokens` / `tokens_per_diff_token` / `seed_bonus_tokens` / `pool_ratio` | 6000 / 30000 / 48000 / 3.0 / 2000 / 0.25 |
| 目录 | `catalog_tokens` | 3000 |

边的权重表也可以通过 `link_weights` 覆盖。另外两个不在 `TriageConfig` 里的参数：`CodeIntel(max_index_bytes=1_000_000)` 和 `Tools(max_line_chars=2000)`。

### 4.4 与最初方案相比的变化

- **增加 `same_directory` 边和相邻打包：** 原因见上，否则不支持精确解析的语言会碎成大量单单元簇。
- **增加规模分层：** 见 ⑤。
- **删除 LLM 规划器：** 原来的 `LiteLLMPlanner` 每个簇调用一次模型来标注，已和对应测试一起删除。调查 agent 落地时，会按工具调用的方式重写模型客户端。`pyproject.toml` 里的 `llm` 可选依赖暂时保留。
- **CLI 变化：** `replay` 改为 `plan`，用于载入已保存的计划。
- **`TokenCounter` 迁到 `review_core.tokens`：** 消除 intel 对 triage 的反向依赖。

## 5. 讨论中确定的取舍

1. **过滤阶段不加 AI。** 两种错误的代价不对称：多审一个单元只浪费几千 token；错排一个单元，召回就永久损失了，后面没有任何环节会再看到它。像“8.6 万字符的一行向量数据”这种情况，问题在于展示，不在于过滤，所以用规模分层加折叠解决。调查 agent 本身就是 AI，看到折叠后的数据行，扫一眼即可。
2. **规模上限按“怎么审”分层，不按“审不审”。** 见 4.2 ⑤。
3. **种子保持现状，不扩展。** 种子不是重点。以后更倾向于把同类能力（引用查找、签名核对、分析器诊断）作为工具提供给 agent，由它自己决定何时使用，而不是由分诊硬性指定。
4. **预算先保证覆盖。** 现在只要求每个簇都有保底预算。后续要补上真正的保证，即**读取覆盖率**：运行时记录 agent 实际读过哪些单元，审完检查每个单元是否至少被读过一次（折叠形式也算）。

## 6. 第 2 阶段：Code Intel 与工具层

这一阶段的目标是：调查 agent 用到的每个工具都输出可读的结果，覆盖 bench 上的主要语言，并且如实说明哪里没有查到、为什么没查到。

### 6.1 完整性语义：limits / gaps / issues

原来只有一个 `complete` 标记，把两类性质完全不同的情况混在了一起：“预算用完，没查完”和“这门语言或这个文件分析不了”。调用方因此无法判断缩小范围后重试有没有用。现在所有结果（`QueryResult`、`ChangeUnit`、`ChangeGraph`、`TriagePlan`、`ToolResult`）都使用同一个模型 `Analyzed`：

| 字段 | 含义 | 调用方能做什么 |
|---|---|---|
| `limits` | 时间或规模预算让查询提前停止，并写明是哪个预算 | 缩小范围后重试，就能看到剩余部分 |
| `gaps` | 范围内有部分内容的分析精度低于声明的精度，带类型和路径 | 重试没有用，改用文本工具 |
| `issues` | 其他失败 | 视具体情况处理 |

`complete` 改为由这三个字段推导出来。缺口（gap）的类型：

| 类型 | 含义 |
|---|---|
| `unsupported` | 该语言没有解析器或符号提取器 |
| `syntax_error` | 文件解析不干净，来自它的结果不完整 |
| `unindexed` | 文件超过大小上限，不解析也不建索引 |
| `unreadable` | 二进制文件、非 UTF-8 编码，或者不是文件内容 |
| `name_only` | 这门语言的绑定只能按名字匹配 |
| `resolver_failed` | 外部解析器运行失败或超时 |

缺口在产生的地方以 `GapError` 的形式抛出。查找引用时，只有提到了目标名字的文件，其解析失败才算缺口；仓库里一个无关的 Ruby 文件不会让 Python 符号的查找变成“不完整”。计划里另外记录了 `gap_counts`，即各类缺口的总数。

### 6.2 语言覆盖与语法容错

- **新增 C# 和 PHP：** 符号、调用和导入都能提取。
  - 符号：类、方法、属性、record、trait；
  - 调用：带接收者的成员调用和静态调用；
  - 可见性按各自语言的默认规则判定，例如 C# 成员默认是 private。
- **Kotlin 没有接入：** 实测 ast-grep 自带的 Kotlin 语法会把 `object` 声明和带修饰符的函数解析错。bench 上也没有 Kotlin 的标注。
- **C++ 后缀补全：** 新增 `.cxx`、`.hh`、`.hxx` 等后缀。`.h` 只有在出现 class、namespace、template、`::` 等 C++ 写法时才按 C++ 解析，否则按 C 解析。
- **C++ 类外定义：** `Foo::bar` 这样的定义现在命名为作用域 `Foo` 下的 `bar`。原来名字是 `Foo::bar`，永远匹配不上调用点。调用名的拆分也加上了 `->`、`?->` 和 `\`。
- **语法错误不再让整个文件失去符号：** ERROR 节点和缺失记号下面的子树会被跳过，其余部分的符号照常提取。大纲会给出 `syntax_error` 缺口，并列出错误所在的行。改动单元在错误区域之外仍然归属到符号（精度记为 `mixed`），区域之内退回按 hunk 归属。
- **性能：** 解析时随遍历携带作用域，不再对每个节点回溯祖先节点；大纲里的父子链接改为字典查找。

### 6.3 类型感知的调用解析

评估（第 9 节）发现：按名字匹配是调用关系准确率低的主要原因。因此，所有主要语言都改用成熟的类型分析工具来判断“这个调用到底调的是哪个函数”，按名字匹配只作为最后的兜底。

#### 选型调研

| 方案 | 结论 |
|---|---|
| GitHub stack-graphs | 上游已于 2025 年 9 月归档。docs.rs 上有一个自称在维护的分支（basemind），但无法确认其活跃度；它的规则本质上也只做名字解析，不做类型推断。不选 |
| SCIP 索引器（scip-typescript、scip-python 等） | 需要为整个仓库建立索引，Node 堆默认要 8GB；按快照逐个建索引成本太高。不选 |
| 各语言的类型检查器 / 编译器前端 | 不需要完整构建也能分析仓库内的代码；可以只回答我们提出的调用点；本来就是 IDE 跳转到定义的底层实现。**选这一路** |
| Python：Jedi 与 Pyrefly | 两者都接入，在 bench 上实测对比（见下表），默认用 Pyrefly |

#### 各语言的实现

| 语言 | 用的轮子 | 实现方式 |
|---|---|---|
| Go | 官方类型检查器 `go/types` | 辅助程序只用 Go 标准库，不下载任何模块：仓库内的包从源码做类型检查，标准库走默认 importer，其余依赖用空的假包代替；类型错误照常容忍。按 `go/build` 的规则处理构建标签，支持 vendor 目录和嵌套模块。原计划用 `golang.org/x/tools/go/packages`，它依赖 `go list` 解析模块，离线时行为不稳定，而且要额外下载，所以改为直接使用 `go/types`。 |
| Java | Spoon 11.5（noclasspath 模式） | 输入是改动文件，加上两类上下文（最多 800 个文件）：一是 import 指向的类型源文件（单类型导入、静态导入、通配导入），二是同目录（同包）的源文件。依赖缺失时，调用如实报告为“未解析”。跨 main/test 源码根目录按包匹配也试过：elasticsearch 用例变慢一倍多，解析率没有提升，已回退。 |
| C/C++ | libclang 18（PyPI `libclang`，自带动态库） | 推测编译参数：语言标准、所有含头文件的目录（`-I`），以及宿主编译器自己的系统搜索路径（`-isystem`，即标准库和 SDK）。pip 版的 libclang 不带任何头文件，最初连 `<string>` 都找不到，大部分 C++ 调用因此解析不出来。只跳过前导部分（preamble）里的函数体。调用一般只能看到头文件里的声明，所以通过 clang 的 USR 关联到 .cpp 里的定义。仍然只能部分解析：Qt、OpenCASCADE 这类不在仓库里的第三方头文件，以及宏，会让一部分调用解析不出来。 |
| TypeScript / JavaScript | TypeScript 6.0 编译器 API（类型检查器） | 读取最近的 `tsconfig`，开启 `allowJs`，不需要 `node_modules`：缺失的包类型为 any，相关调用保持“未解析”。能正确处理 `this.x()`、继承来的方法、别名导入、默认导出和 CommonJS 的 `require`。没有用 TypeScript 7：它是 Go 原生实现，原有的 JS 编译器 API 已经不再提供。 |
| Python | Pyrefly 1.4（Meta，通过 LSP 调用；备选 Jedi 0.20） | 每个导出目录写入一份 `pyrefly.toml`：搜索路径只包含仓库自己的源码根目录（所有最外层包的父目录，加上 `.` 和 `src`），不查询解释器，也不读取 site-packages。定义停在“导入外部模块”的语句上时，记为“绑定到仓库外”。设置 `REVIEW_CORE_PYTHON_RESOLVER=jedi` 可以改用 Jedi。 |

#### Python：Jedi 与 Pyrefly 的对比

在 bench 上 25 个 Python 用例的全部调用点上实测（每个改动文件最多取 400 个调用点）：

| | Jedi 0.20 | Pyrefly 1.4（配置搜索路径后） |
|---|---|---|
| 绑定到仓库内的定义 | 25% | 33% |
| 绑定到仓库外 | 39% | 39% |
| 未解析 | 36% | 28% |
| 单个用例耗时（中位数 / 最大） | 21 秒 / 74 秒 | 0.4 秒 / 1.7 秒 |

- **两者都能绑定的调用点：** 结果相同的 3,872 处，结果不同的 416 处。不同的主要是构造函数调用，Jedi 指向类，Pyrefly 指向 `__init__`，两种都正确，映射到符号后结果一致。
- **只有一方能绑定：** 只有 Pyrefly 能绑定的有 1,447 处，只有 Jedi 能绑定的有 155 处（多是对未标注类型的属性做推断）。
- **一个必须修的问题：** 不配置搜索路径时，Pyrefly 找不到仓库根目录下的包，定义会停在 import 语句上；配置后解决。

#### 名字匹配兜底：按调用形式过滤

解析器给不出答案的调用点（以及 Rust、C#、PHP 的全部调用点）仍然按名字匹配，但会先按调用的形式排除不可能的候选：

- **`self.m()` / `this.m()`：** 只考虑方法，优先选外层类自己的方法；
- **`Name.m()`、`ns::m()`：** 优先选类（或命名空间）`Name` 的成员；
- **`obj.m()`：** 只考虑方法，不考虑顶层函数；
- **`f()`：** Python、JS/TS、Go、Rust 里只考虑自由函数；Java 这类语言里，再加上外层类自己的方法。

通过 import 绑定得到的候选，以及类型解析得到的候选，都不参与过滤。

#### 协议与降级

- **独立进程、同一份协议：** 所有解析器都是独立的辅助进程，使用同一份 JSON 协议（见 `intel/resolvers/__init__.py`）。请求是导出目录、文件列表和调用点；响应是每个调用点解析到的声明，可以标记为“绑定到仓库外”（例如标准库），C++ 另外返回各个定义的 USR。核心代码只依赖这份协议。
- **导出文件：** 需要的文件按提交导出到 `.state/.../exports/<sha>/`，同一提交内复用。各语言需要导出的文件：
  - Go：整个仓库的 `.go` 文件和 `go.mod`；
  - C++：全部头文件；
  - TypeScript/JS：全部 JS/TS 源文件和 `tsconfig`、`package.json`；
  - Python：全部 `.py` 文件；
  - Java：只需要被请求的文件。
- **辅助程序的构建：** Go 和 Java 的辅助程序在第一次使用时，按源码摘要编译到 `~/.cache/review-core/build/`（可用 `REVIEW_CORE_CACHE` 指定位置）。
- **结果缓存：** 解析结果按（解析器版本、提交、文件集合、调用点）缓存在 SQLite 里，相同输入不会重复运行。
- **按声明名映射：** 解析器报告的是被绑定声明自己的名字。只有同名的符号才会被选中（构造函数映射到它所在的类），所以遮蔽了函数的参数或局部变量不会被误当成外层函数。
- **未解析也要报告：** 解析器没能绑定的调用点按语言统计，作为 `name_only` 缺口报告（例如“java on head: 1 of 2 call sites not bound by type”），不会悄悄退回按名字匹配。
- **工具链缺失：** 解析器自动停用，继续按名字匹配，并报告 `name_only` 缺口。
- **解析器出错：** 报告 `resolver_failed` 缺口，同样退回按名字匹配。
- **整体关闭：** `REVIEW_CORE_RESOLVERS=off` 关闭全部解析器，用于消融实验，或在不装这些工具链的环境里运行。

#### 用在哪里

- **改动图：** 每一侧（base/head）、每门语言只运行一次辅助进程，全部改动文件都作为上下文。调用点被确定绑定时，生成 `bound` 边；绑定到不在改动里的符号，或者绑定到仓库外时，不生成边，也不再按名字猜。只有解析器给不出答案的调用点，才退回按名字匹配。
- **`find_definition`：** 用调用所在文件，加上全仓库里命中目标名字的文件（最多 200 个）作为输入。
- **`find_references`：** 用预筛出来的候选文件批量解析，只保留确实绑定到目标符号的调用点。

#### 部署与依赖

这些工具都是**可选依赖**，`review_core` 的核心依赖没有变化（`pip install` 不会安装它们）。没有安装时，一切照常运行，只是这几门语言退回按名字匹配，并报告为缺口。

| 能力 | 部署时需要 | 体积（约） |
|---|---|---|
| Go 解析 | Go 工具链 1.22+（`REVIEW_CORE_GO` 或 PATH） | 250MB |
| Java 解析 | Java 17+ 运行时（`REVIEW_CORE_JAVA` / `JAVA_HOME`）和 Spoon 的 jar-with-dependencies（`REVIEW_CORE_SPOON_JAR`，或放到缓存目录 `spoon/` 下） | 300MB + 15MB |
| C/C++ 解析 | `pip install 'gitlab-review-core[cpp]'`（libclang）；宿主机上有 clang 或 gcc 时，会自动使用它的系统头文件路径（`REVIEW_CORE_CXX` 可指定编译器） | 25MB |
| TypeScript/JS 解析 | Node.js（`REVIEW_CORE_NODE` 或 PATH），以及 `typescript@6`（`REVIEW_CORE_TYPESCRIPT`，或安装到缓存目录 `node/node_modules/` 下） | Node 自带 + 23MB |
| Python 解析 | `pip install 'gitlab-review-core[python]'`（pyrefly；jedi 为备选） | 20MB |

所以接入业务时，可以按代码库的语言选择装哪几个，Docker 镜像也可以分精简版和全量版两种。这些辅助程序只解析代码，不构建、不运行被审查的代码，也不访问网络：Go 运行时设置了 `GOPROXY=off`，Pyrefly 不查询解释器、不读 site-packages，TypeScript 的 `maxNodeModuleJsDepth` 设为 0，Java 和 C++ 本来就不联网。

### 6.4 引用查找

- **候选预筛：** 查找调用方和导入方时，先对目标的名字、导出名和模块文件名做一次按词的 `git grep`，只解析命中的文件。别名导入仍然会出现目标名字或它的模块名；默认导入和命名空间导入靠模块文件名命中。原来是逐个解析全仓库的文件，大仓库上很容易触发时限。
- **调用方的定义查找范围：** 判断一个调用点是否调用了目标时，只在目标文件和调用所在文件里找定义，不再对全仓库搜索。
- **变量遮蔽判定：** 每个文件只建一次索引，不再对每个调用点重新解析整个文件。
- **改名候选：** 现在要求两边的规范化 token 都至少有 24 个，相似度至少 0.8。过小的函数体之间天然相似，以前会产生很多误连。比较对数的上限改为惰性截断，不再先构造完整的笛卡尔积。

### 6.5 工具层：给 agent 的界面

- **文本输出：** 每次调用返回给模型的是文本：带行号的源码、每行一条结果、长行折叠、总长度有上限。同时附上本次展示的结构化条目，供程序使用。完整结果存为证据，可以用文本里显示的 12 位短编号查到。
- **结尾的状态行：** 文本末尾统一给出：
  - 下一页的 offset；
  - `INCOMPLETE`：触发了哪个时限或规模上限，提示缩小范围；
  - `PARTIAL`：各类缺口的数量和示例，并提示文本工具在这些地方仍然可用；
  - `ISSUES` 和 `ERROR`；
  - 证据编号。

  这样 agent 不会把“没找到”误当成“不存在”。
- **`read_diff`：**
  - 按 hunk 分页，可以跨文件；
  - 可以按文件、单元（`U#`）、簇（`C#`）或全部来看；
  - 每行标注它所在那一侧的行号：`-L` 是 base 行，`+L` 和普通行是 head 行；
  - hunk 头部标出它所属的单元；
  - 单个 hunk 超出上限时，可以用 `line_offset` 在 hunk 内部按行续读。
- **短编号：** Tools 拿到分诊计划后，`read_symbol`、`compare_symbol` 和 `find_references` 都接受 `U#`。
- **错误处理：** 参数错误会指出是哪个字段出了问题；工具内部抛出意外异常时，返回一条错误结果，不会让整个调查中断。
- **按簇简报（`Triage.brief`，CLI 命令 `brief`）：** 内容依次是：任务说明、预算（默认显示无单位的预算值；agent 运行时传入带单位的预算说明，见 10.5）、排序理由、单元列表（`+L`/`-L` 分别标注各侧的行范围）、用文字描述的单元间关系、初始假设、分析不完整时的警告，最后是全局改动目录。

## 7. bench 实测（189 个可用用例）

测量方法：对 189 个可用用例逐个运行“构图 + 分诊”，4 个进程并行，每个用例限时 240 秒。7.1–7.3 是第 1 阶段结束时（纯格式判定修复之后，见 4.2 ①）的数据，7.4 是第 2 阶段结束时的数据。

### 7.1 运行结果

- **全部出计划：** 189 个用例全部出计划，没有超时，也没有报错，全量耗时 65 秒。
- **单个用例耗时：** 中位数 0.6 秒，P90 2.9 秒，最长 27.7 秒。这是语法缓存失效后（语法规范化规则有改动）的冷启动数字；缓存预热后，全量耗时 39 秒，单个用例最长 14 秒。
- **完整性：** 35 个用例的计划标记为 `complete`。其余用例不完整，多数是因为涉及的语言不支持导入绑定解析（如 Java），或文件有语法错误。当时这两类原因混在同一个标记里，第 2 阶段已拆开（6.1）。

### 7.2 计划形态

| 指标 | 中位数 | P90 | 最大 |
|---|---|---|---|
| 每个用例的簇数 | 2 | 5 | 16 |
| 单单元簇数 | 0 | 1 | 3 |
| 初始总预算（token） | 20,736 | 59,512 | 218,752 |

  - `n8n@77ece2e`：21.9 万 token，16 个簇；

  - `ollama@498792c`：一个 46 万 token 的向量数据单元，预算从 3 万降到 6000；
  - `typescript-go` 的两个用例：各有一个约 1.3MB 的文件不建索引，单独成簇。

  另有 2 个簇超过聚类容量（`oversized`），没有被拆分。
- **种子：** 35 个用例产生了种子，共 143 个：调用处未改 119 个，悬空引用 24 个。
- **簇内的边：**

  | 边 | 数量 |
  |---|---|
  | `mention` | 1,712 |
  | `locality` | 1,393 |
  | `same_file` | 1,252 |
  | `call` | 1,081 |
  | `import` | 815 |
  | `test_reference` | 742 |
  | `same_directory` | 563 |

  不依赖语言解析的 `mention` 和 `locality` 是数量最多的两类，说明没有它们，相当一部分改动会落成单单元簇。
- **改动目录：** 5 个用例的目录退化到了按文件汇总。

### 7.3 构图超时的定位与修复

第一轮实测时有 19 个用例在构图阶段超时，大部分是 elasticsearch，其余包括 three.js、nodejs、FreeCAD 等。逐个做性能分析后，找到的原因和修复如下：

| 原因 | 修复 | 提交 |
|---|---|---|
| 构图时，每个调用点都对全仓库做一次 `git grep`，再解析几百个候选文件；而只有改动文件里的定义才能成为边，这些工作全部白做 | 构图时把定义查找范围限定在改动文件（`resolve(within=...)`） | `12dfb34` |
| 每查一个文件就启动 git 子进程（查属性、读内容），elasticsearch 一个用例 120 秒内启动了约 6800 次 | 用常驻的 `git cat-file --batch` 进程读内容；属性按整棵树一次 `check-attr --stdin` 查完；文件大小取自 `ls-tree -l` | `12dfb34`、`d0427f3` |
| 有语法错误的文件解析失败不缓存，每次查询都重新解析（FreeCAD 一个用例解析了 5489 次） | 解析失败也写入缓存 | `52e8ff5` |
| 改动图不完整时不缓存，分诊会再构建一次 | 不完整的图也缓存 | `12dfb34` |

另外加了兜底：构图有总时限（`CodeIntel.graph_timeout`，默认 60 秒）。超时后停止精确的调用解析，保留廉价的边，并在 issues 里记录有多少个调用点没解析；分诊照常出计划。

效果：`elasticsearch@5e604e4` 从超过 240 秒降到 2.5 秒，FreeCAD 从跑满 60 秒的时限降到约 10 秒（冷启动）。

## 9. 解析质量评估

第 2 阶段结束后，对 Code Intel 做了一次逐层的质量评估：先找出“显示成功、实际出错”的问题并修复，再针对调用关系的准确率接入更多解析器。下面是方法和结果。

### 9.1 符号提取：与权威解析器对比

对 bench 里所有改动文件，把我们提取的符号与权威解析器的结果对比：Python 用标准库 `ast`，Go 用官方 `go/parser`，Java 用 Spoon，C/C++ 用 libclang。

**对比中发现并修复的问题。** 这些情况下，大纲显示成功，结果却是错的：

| 问题 | 影响 |
|---|---|
| C/C++ 把类型引用（`struct foo *p`）当成了符号 | C 文件里多出约 4,900 个假符号 |
| ERROR 节点会吞掉其中完好的定义 | electron 的 `web_contents.cc` 286 个符号全部丢失；修复后找回 275 个 |
| C++ 返回引用的函数（`T& f()`）名字取错；`class A::B` 没有拆出限定名；C 的 `typedef struct {...} Name` 没有名字 | 名字不对，调用永远匹配不上 |
| Go 的类型别名、Java 的注解类型 | 漏掉 |

**修复后的一致率：**

| 语言 | 一致率 |
|---|---|
| Python | 100% |
| Go | 100% |
| Java | 约 100%（剩下的差异是 Spoon 给局部类的命名方式不同） |
| C | 99% |
| C++ | 88% |

C++ 剩下的损失主要在宏造成的语法错误区域里。我们这边多出来的符号，抽查下来基本都是 libclang 自己因为缺少头文件而没有解析出来的真实定义。

**“显示完整、实际不完整”的问题。** 解析器没能绑定的调用点，原来会悄悄退回按名字匹配，结果里却不报告任何缺口。现在作为 `name_only` 缺口如实报告。

## 10. 第 3 阶段第一轮：审查 agent

### 10.1 目标与验收

第一轮只要求**不明显差于 OCR**。OCR 和我们的系统都用 GPT-6.1 Sol 和一个小型开源 Qwen 模型，在 dev 集上各跑 3 次，按官方评测器打分。OCR 的分数由我们自己重跑，不沿用论文里的数字。

| 指标 | 通过条件（两个模型都要满足） |
|---|---|
| SEM-F1 | 我们减 OCR 的差值 ≥ −max(2 个百分点, 2 倍重复运行标准差) |
| Token | 每个用例平均不超过 OCR 的 1.5 倍 |
| 稳定性 | 失败或报错的用例不超过 1% |
| 后训练准备 | 轨迹完整；回放逐字节一致；SFT 导出可用 |

数据划分：smoke 集（10 个用例）用于调试，calibration 集（41 个）用于调参数，holdout 集（40 个）第一轮不使用。dev 集有 115 个用例，其中 110 个的源码可用，所以实际评测 110 个。

### 10.2 第一轮的范围

| 做 | 留到后面 |
|---|---|
| 每个簇对应一个审查回合（ReAct） | 反驳 agent（第二轮，用来提高精确率） |
| 确定性编排器 | 沙箱 |
| 工作记忆 L0 到 L2 | L3：用 LLM 压缩上下文 |
| 汇总：过滤、去重、排序、截断 | 长期记忆；从共享池申请追加预算 |
| 轨迹记录、回放、SFT 导出、把评测命中写回轨迹 | RL 训练本身 |

### 10.3 结构

```
分诊计划 → 编排器（确定性，各簇并行）
             └─ 每个簇一个回合：Policy ⇄ ReAct 循环 ⇄ InvestigateEnv（工具、发现、预算）
                                  └─ ContextManager（工作记忆）
          → 汇总 → 评论（每条都能追溯到所在回合和发现）
```

包 `review_agent/` 的内容：

| 模块 | 职责 |
|---|---|
| `policy` | 模型边界，消息一律用 OpenAI 格式。`LiteLLMPolicy` 只重试传输层错误；`ScriptedPolicy` 供测试用；`ReplayPolicy` 回放轨迹，请求与记录不一致时直接报错 |
| `env` | `ReviewEnv` 的接口形状与 rLLM 的 `BaseEnv` 一致：`from_dict`、`reset`、`step`。`InvestigateEnv` 负责工具、发现和预算计量。参数错误或调用了不存在的工具时，作为观察结果返回给模型，不中断回合 |
| `agent` | ReAct 循环。结束方式有：调用 finish、预算用完（先提示收尾，再给 2 轮）、上下文用满、超过步数上限、连续不调用工具（提醒 2 次后结束） |
| `context` | 工作记忆，见 10.5 |
| `findings` | 发现的数据结构，以及按代码片段定位行号 |
| `aggregate` | 汇总规则 |
| `orchestrator` | 编排一次完整审查。中断后重跑时，已保存的回合直接复用 |
| `trajectory` | 轨迹格式与 SFT 导出 |
| `prompts` | 提示词，带版本号 |

**线程模型：** 同一用例的各簇共享一个 CodeIntel，对 review_core 的访问用一把锁串行，模型调用在锁外，可以并行。不同用例之间按用例并行。存储层每次调用都新开 SQLite 连接，所以并发安全。

### 10.4 工具（14 个）

| 分组 | 工具 |
|---|---|
| 看改动 | `read_diff`（可一次传多个路径；路径没有 diff 时，列出有 diff 的文件）、`compare_symbol`、`list_changes`（新增：列出全部单元及其所属簇，并列出被规则排除的文件） |
| 看代码 | `outline`、`read_symbol`、`read_file`、`find_file`（新增：按路径子串查找文件） |
| 追关系 | `find_definition`、`find_references` |
| 搜索 | `code_search`（新增正则、大小写和排除路径选项）、`structural_search` |
| 输出 | `report_finding`（一次可报多条）、`update_finding`、`finish` |

讨论时说过一共 15 个工具，那是数错了，实际是 14 个。

**参考 OCR 的地方：** OCR 一共只有 6 个工具（`task_done`、`code_comment`、`file_read`、`file_read_diff`、`file_find`、`code_search`），我们的工具覆盖了它全部的功能。我们借鉴了四点：用代码片段定位评论、一次报多条、一次读多个文件的 diff、正则搜索。

**schema 精简：** 工具 schema 每次调用都会发送。原始的 pydantic schema 约 3,400 token。去掉字段标题、内联 `$ref`、把可选字段写成普通类型之后，降到约 2,400 token，这样对小模型和服务端的工具解析器也更友好。工具版本号是 `tools-v2+investigator-v1`，记录在每条轨迹里。

### 10.5 预算与工作记忆

**预算：** 每个回合的预算 = （簇的预算值 + 按比例分到的共享池）× `budget_scale`，单位是模型输入加输出的 token 数。默认 `budget_scale = 10`，这个值**没有校准过**，要在 calibration 集上按“每个用例的 token 数不超过 OCR 的 1.5 倍”来定。每次工具结果之后都会显示当前用量；超过预算时提示收尾，再给 2 轮。provider 不返回用量时，用 tiktoken 估算。

**工作记忆（第一轮）：**
- **L0：** 工具输出有上限，长结果分页（第 2 阶段已完成）。
- **L1：** 环境维护一个确定性的进度账本：已报告的发现、本簇里还没读过 diff 的单元、预算用量。每次遮蔽之后，把它作为一条消息追加到上下文末尾。
- **L2：** 观察遮蔽。上下文超过窗口的 60% 时，把最近 6 条以前的工具输出替换成一行占位文字，注明工具名和证据编号。替换是批量进行的，一旦替换就不再恢复，所以只有在遮蔽发生的时刻上下文才会改变，前缀缓存不受影响。这个做法依据 Lindenbauer 等人 2025 年的论文 *The Complexity Trap*：在 SWE-bench 上，观察遮蔽和 LLM 摘要效果相当，成本更低。
- **L3：** 还没有做。遮蔽之后仍超过窗口的 85% 时，提示模型报告剩余的发现并结束。
- **上下文窗口：** 默认 64k，小模型计划用 32k。

### 10.6 评论定位与汇总

**定位：** `report_finding` 不接收模型写的行号，而是接收一段代码原文（`existing_code`），由程序依次在下列位置查找：diff 新侧 → diff 旧侧 → head 文件 → base 文件。先找完全一致的，再找忽略空白后一致的；代码前面的行号前缀（如 `+L12`、`* L5`）会被去掉。有多处匹配时，优先选落在改动行上的，其次选离 `line_hint` 最近的。找不到就把原因告诉模型，让它修正。

另外要更正讨论时的一个说法：当前默认的 AACR 指标是**文件级**语义匹配，裁判模型的提示词明确要求忽略具体行号。所以在这个指标下，片段定位的主要价值是保证路径正确、行号真实，以及避免行号错误混进训练数据，而不是直接提高匹配率。

**证据：** 每条发现都必须引用本回合工具结果里出现过的证据编号，否则拒收。

**汇总规则：**
1. 去掉已撤回的发现。严重程度默认不过滤（`min_severity` 默认 `nit`，可以配置）。
2. 排序：严重程度 → 是否在 diff 内 → 簇的排名 → 位置。
3. 去重：同一文件、同一侧、行号相距不超过 3 行，并且代码片段相同或标题词重合度 ≥ 0.5。被去掉的重复项记录在保留项的 `duplicates` 里。
4. 默认不截断条数（`max_comments`）。
5. 评论正文 = 标题 + 描述；是否附上修复建议可以配置，这一项留作 M4 的对照实验。

### 10.7 后训练兼容与 bench 适配

**轨迹（`episode-v1`）：** 每一步记录模型实际收到的请求，存成消息哈希的列表，指向回合内的消息表，避免长回合的存储量按平方增长。此外还记录模型回复、用量、各工具的观察结果，以及这一步之前上下文发生的变化（遮蔽、进度账本、提醒、收尾提示）。

**回放：** 用 `ReplayPolicy` 在新环境里重跑，结果与原回合逐字节一致，这一点有测试覆盖。

**SFT 导出：** 采用 OpenAI 微调格式，助手消息带 `weight` 字段。上下文只增不改的连续步骤合成一个样本；遮蔽发生时开始新样本。继承自前一段的助手消息权重为 0，所以每个模型决策都只在它当时实际看到的上下文里训练一次。

**评分写回：** `grade` 命令把官方评测的命中结果按溯源信息（回合、发现）写入 `grades.jsonl`，可以直接作为 RL 奖励或拒绝采样的依据。`export-sft --only-hits` 只导出产出过命中评论的回合。

**bench 命令（`review-bench-aacr`）：**

| 命令 | 作用 |
|---|---|
| `review` | 跑我们的系统，结果按 OCR 的格式写出，官方评测器可以直接读 |
| `ocr` | 跑 OCR 基线 |
| `evaluate` | 用官方 `evaluate.py` 打分，裁判模型可以指定 |
| `compare` | 两个系统多次运行的均值和标准差，按用例做配对 bootstrap，并逐项判断是否满足第一轮通过条件 |
| `grade`、`export-sft` | 评分写回与训练数据导出 |

**公平性：**
- OCR 版本固定为发布满两周的 1.13.3，二进制的校验和与官方 release 一致。参数采用 AACR 评测适配器的默认值（`max-tools 30`，OCR 内部会提高到最低值 50；并发 8；超时 10 分钟）。
- 两个系统用同一个网关、同一个模型、同一批用例、同一个 diff 范围（merge-base…head）。bench 的仓库缓存不含完整历史，OCR 自己计算 merge-base 时会失败，所以为它构造一个只有两个提交的临时仓库，两个提交的文件树与 base、head 完全相同。不写入缓存。
- 每个尝试过的用例都会写出结果文件；失败的用例记为没有评论，计入分母，不会因为失败而被排除在外。
